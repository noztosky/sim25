# AirSim Engine Modification for Dynamic Physics Period

본 문서는 시뮬레이터 물리 엔진의 업데이트 속도를 동적으로 조정하기 위해 AirSim 커널에 적용된 수정 사항을 기록합니다.

## 1. 수정 배경
기존 AirSim은 물리 루프 주기(`physics_loop_period_`)가 코드 내에 하드코딩되어 있어, 주파수 변경 시마다 언리얼 프로젝트의 리빌드가 필요했습니다. 벤치마크 효율성을 높이기 위해 이를 `settings.json`에서 직접 제어할 수 있도록 개선하였습니다.

## 2. 주요 수정 사항

### 2.1 SimModeWorldBase.h
- `physics_loop_period_` 멤버 변수의 기본값을 1ms(1,000,000ns)로 표준화.
- 외부(SimModeWorldBase.cpp)에서 이 값을 안전하게 덮어쓸 수 있도록 구조 확인.

### 2.2 SimModeWorldBase.cpp (핵심 로직)
`initializeForPlay()` 함수 내에 다음 로직을 추가하여 시뮬레이션 시작 시 설정을 주입하도록 수정되었습니다.

```cpp
// settings.json에서 "PhysicsLoopPeriod" 항목을 읽어옴 (기본값: 현재 엔진 설정값)
long long period = msr::airlib::Settings::singleton().getInt("PhysicsLoopPeriod", (int)getPhysicsLoopPeriod());

// 읽어온 값을 물리 커널 주기에 즉시 반영
setPhysicsLoopPeriod(period);
```

## 3. 주파수별 설정 가이드 (settings.json)
수정 후에는 아래와 같이 `PhysicsLoopPeriod`(단위: Nanoseconds) 값을 조정하여 엔진 속도를 제어할 수 있습니다.

- **1 kHz**: `"PhysicsLoopPeriod": 1000000`
- **4 kHz**: `"PhysicsLoopPeriod": 250000`
- **8 kHz**: `"PhysicsLoopPeriod": 125000`

## 4. 시사점
이 수정을 통해 벤치마크 실험 시 **시뮬레이터 재빌드 없이 `settings.json` 수정 및 시뮬레이터 재시작만으로** 다양한 환경에서의 통신 성능을 즉각적으로 비교 분석할 수 있게 되었습니다. 이는 논문 실험의 변수 통제 및 재현성을 확보하는 핵심 설계 요소입니다.

## 5. SHM 텔레메트리 전송 방식 최적화 (2026-06-29)
### 5.1 개요 및 목적
본 실험 및 연구의 핵심 목적은 단순히 지표상으로 그럴듯하게 보이는 목표 주파수(예: 1000Hz) 수치를 달성하는 것이 아닙니다. 제어 수신단(예: EKF 상태 추정기, 비행 제어 알고리즘)이 받아들이는 **실제 센서 데이터의 물리적 품질(Quality of Data)을 극대화**하고, 가상 환경과 실환경 간의 **시간 동기화 특성을 투명하게 반영**하는 것이 본질적인 지향점입니다.

기존 코드에 적용되어 있던 보정용 `while` 루프(Catch-up Loop)는 물리 엔진이 지연되어 유실된 주기를 보정하기 위해 한 물리 틱 내에서 동일한 데이터를 타임스탬프만 가공하여 몰아치기 방식으로 발행(Batching)하도록 구현되어 있었습니다. 이는 겉보기에는 목표 주파수를 맞추는 것처럼 보이지만, 데이터의 실질적인 물리적 품질 측면에서는 치명적인 위해를 끼칩니다.

### 5.2 기존 보정 방식(Batching)의 과학적 문제점
* **정보 엔트로피 제로 (Zero-Information Updates) 및 필터 교란:** 물리적인 드론의 위치, 속도, 가속도 상태는 전혀 업데이트되지 않았음에도, 시간 축만 강제로 쪼개어 동일한 상태를 여러 번 중복 송신하게 됩니다. 이는 칼만 필터(EKF) 등 상태 추정 알고리즘의 공분산(Covariance) 행렬 계산을 교란하여 필터 추정 오차를 누적시키고 제어 계통의 안정성을 떨어뜨립니다.
* **가짜 지터(Fake Jitter)와 판독 불가:** 순간적으로 0.1us 간격으로 폭발하는 패킷 전송 특성은 실제 하드웨어 센서에서 발생할 수 없는 불연속적인 입력 신호입니다. 이는 OS 스케줄링이나 네트워크 병목으로 인한 실제 지터(Jitter) 성분을 덮어씌워 제어 시스템의 지연 현상을 정확히 진단하거나 보상하는 알고리즘을 설계하는 것을 불가능하게 만듭니다.

### 5.3 개선 사항
실제 비행 제어 및 시뮬레이션 환경의 사실감(Fidelity)과 정직한 벤치마크 데이터를 얻기 위해 다음과 같이 코드를 개선했습니다:
* **물리 업데이트와 텔레메트리의 1:1 매핑 보장:** 보정용 `while` 루프를 완전히 걷어내고 `if` 조건문으로 교체했습니다. 이로써 물리 엔진이 실제로 상태를 갱신(1회 호출)하는 시점에 정확히 1개의 데이터만 텔레메트리로 정직하게 송신됩니다.
* **사실적인 실시간 스케줄링 지터 반영:** 지연이 발생할 경우 데이터 전송 역시 그 지연을 있는 그대로 반영하게 되므로, 수신 제어 측에서 실제 시뮬레이션 타임 스레드의 실시간 성능 저하 및 물리적 시간 편차를 명확하게 관측하고 이에 최적화된 동적 제어/상태 예측을 수행할 수 있게 됩니다.
* **정수 기반의 정직한 다운샘플링:** 물리 엔진이 설정된 `ShmSampleHz`보다 더 고주파(예: 8000Hz)로 구동될 때는 누적 연산이나 배칭 없이, 정확한 다음 전송 타임스탬프 도달 시점에만 1회씩 추출하여 전달(다운샘플링)하도록 구현했습니다.
